# Komga Smart Scan — External Diff Tool (PDF-only)

> External Python tool that pre-computes library diffs for **PDF-only**
> libraries and drives targeted Komga API calls, avoiding the full
> `ScanLibrary` pipeline. Requires one new REST endpoint in Komga to support
> creating series + books from disk paths.

---

## 1. Problem Statement (unchanged)

Komga's `ScanLibrary` is slow for large libraries:

| Phase | Bottleneck |
|---|---|
| Phase 1.6 — Reconcile | `tryRestoreSeries/Books()` reads entire files for hashing. N+1 DB queries. Full library loaded into memory. |
| Phase 2 — Fan-out | `analyzeUnknownAndOutdatedBooks()` scans ALL books, emits thousands of tasks. |
| Task queue drain | AnalyzeBook → RefreshBook → RefreshSeries → AggregateSeries run sequentially per series. |

**Goal:** Externally compute what changed, then call Komga REST API only for those
changes — skipping the monolithic reconcile + fan-out pipeline entirely.

### 2.1 Motivation

|---|---|

## 3. Step-by-Step Feature Flow

### Step 1: Choose Library

**UI:**
- Fetch and display all libraries from Komga API as cards
- Each card shows: library name, ID, root path
- Click a card to select → advances to Step 2

**Backend:**
- `GET /api/libraries` → `api.list_libraries()`

### Step 2: Scan DB & FS

**UI:**
- Display selected library info (name, ID, root)
- Toggle: "🔐 Compute file hashes (SHA-256)" — default ON
- "Run Scan" button
- Progress indicator while scan runs
- On completion:
  - Summary: DB series/books count, FS series/files count
  - Diff table: new series, deleted series, new books, deleted books, changed books, pending hash
  - Download links for 3 JSON files:
    1. `{request_id}_db.json` — DB snapshot
    2. `{request_id}_fs.json` — FS snapshot (with/without hashes)
    3. `{request_id}_diff.json` — comparison result
  - "Next → Generate Curls" button → advances to Step 3

**Backend:**
- `POST /api/scan` `{library_id, hash_files: bool}`
  1. Creates request ID (`YYYYMMDD-HHMMSS`)
  2. Creates folder `/exports/{request_id}/`
  3. Reads DB → saves `{request_id}_db.json`
  4. Walks FS (with optional hashing) → saves `{request_id}_fs.json`
  5. Computes diff → saves `{request_id}_diff.json`
  6. Returns: `{request_id, summary, file_paths}`

### Step 3: Generate Curls

**UI:**
- Display previous scan summary
- Checkbox multi-select for change categories (all checked by default):
  - ☑ New series
  - ☑ Deleted series
  - ☑ New books
  - ☑ Deleted books
  - ☑ Changed books
  - ☑ Hash book (DB missing hash, FS has hash — calls analyze to compute it)
- Toggles for optional actions:
  - ☑ Analyze books (post-create + changed books)
  - ☑ Refresh metadata (books + series)
- "Generate" button
- On completion:
  - List of generated curl files (one per category + combined)
  - Download button for each file
  - "Execute" button next to each file → advances to Step 4 (or opens Step 4 pre-selected)

**Backend:**
- `POST /api/curl` `{request_id, categories: [...], analyze: bool, refresh: bool}`
  1. Reads `{request_id}_diff.json`
  2. Generates bash script per selected category:
     - `{request_id}_new_series.sh`
     - `{request_id}_deleted_series.sh`
     - `{request_id}_new_books.sh` — POSTs to `/api/v1/series/{id}/books` per book
     - `{request_id}_deleted_books.sh`
     - `{request_id}_changed_books.sh`
     - `{request_id}_pending_hash.sh` — POSTs analyze for each book missing DB hash
     - `{request_id}_all.sh` (combined — only if >1 category selected)
  3. Returns: `{script_paths: {...}}`

### Step 4: Execute Curls

**UI:**
- Display list of available curl scripts for the request ID
- "Execute" button next to each script
- When executing:
  - Live SSE stream of output (success/failure per command)
  - Progress bar (X of Y commands)
  - Color-coded log lines
- Dashboard summary after completion:
  - Total commands attempted / succeeded / failed
  - List of failures with error messages
- "Download Log" button to save execution log as text file

**Backend:**
- `POST /api/execute` `{request_id, script_name}`
  - Reads the script file
  - Parses individual curl commands
  - Executes each command via `subprocess.Popen`
  - Streams output via SSE: `{command_index, total, success, output, error}`
- `GET /api/execute/{request_id}/log` — returns execution log as text file
- `GET /api/exports/{request_id}/{filename}` — download any file from the request folder

## 6. Pending Hash — New Category

### 6.1 Problem
When `hash_files=True` on scan, the FS walker computes XXH3_128 hashes for every file. But the DB may have `file_hash = ""` for books that Komga hasn't analyzed yet. These books haven't changed — they just lack a DB-side hash for comparison. They should appear as a separate "pending hash" category rather than being silently ignored.

### 6.2 Solution
**Step 2 (Scan):** Diff results include a `pending_hash` row showing books where FS has a hash but DB hash is empty.

**Step 3 (Curls):** The `pending_hash` category generates `POST /api/v1/books/{id}/analyze` commands. This triggers Komga's analyzer to open the file, compute its XXH3_128 hash, and store it in the DB. On the next scan, these books will have matching hashes and can use hash-based change detection.

### 6.3 Changes needed

| File | Change |
|---|---|
| `diff.py` | Add `pending_hash: list[dict]` to `Diff` dataclass. In `compute()`, when `fs_hash` exists but `db_hash` is empty, add to `pending_hash` instead of skipping silently. |
| `server.py` | Add `pending_hash` to scan response totals, add `has_pending_hash` boolean, include `pending_hash` in the diff JSON and raw data. |
| `applier.py` | Add `_bld_pending_hash(diff)` function — generates `curl -X POST /api/v1/books/{id}/analyze` commands. Register `"pending_hash"` in the `builders` dict. |
| `static/app.js` | Step 2: Show "Hash book" row in diff table. Step 3: Add "Hash book" checkbox to category selection. Execute step: handles `pending_hash` script name. |

## 7. Add Books to Existing Series — New Komga Endpoint

### 7.1 Problem
The scanner detects new books inside existing series directories but has no way
to register them via API. Currently `_bld_new_books` falls back to triggering a
full `POST /api/v1/libraries/{id}/scan?deep=false`, which defeats the purpose
of the smart scanner.

### 7.2 Solution
Add `POST /api/v1/series/{seriesId}/books` to `SeriesController` that registers new books already on disk into an existing series — the same logic Komga runs during its own scan in `LibraryContentLifecycle.kt:330-335`.

### 7.3 Existing Code to Replicate

From `LibraryContentLifecycle.kt` (the scan reconcile phase for an existing series):

```kotlin
// line 330-335

    existingActiveBooksByUrl.containsKey(newBook.url)
}
seriesLifecycle.addBooks(existingSeries, booksToAdd)
tryRestoreBooks(booksToAdd)  // optional — expensive (computes hashes)
metrics.addedBooks += booksToAdd.size

```

From `SeriesLifecycle.addBooks()` (lines 121-149):

```kotlin
fun addBooks(series: Series, booksToAdd: Collection<Book>) {
    booksToAdd.forEach {
        check(it.libraryId == series.libraryId)
    }
    val toAdd = booksToAdd.map { it.copy(seriesId = series.id) }

    transactionTemplate.executeWithoutResult {
        bookRepository.insert(toAdd)
        mediaRepository.insert(toAdd.map { Media(bookId = it.id) })
        toAdd.map { BookMetadata(title = it.name, ...) }
            .let { bookMetadataRepository.insert(it) }
    }

    toAdd.forEach { eventPublisher.publishEvent(DomainEvent.BookAdded(it)) }
}
```

### 7.4 DTO

```kotlin

data class AddBooksToSeriesDto(
    @Schema(description = "Library ID the series belongs to", required = true)
    val libraryId: String,

    @Schema(description = "Books to register (already on disk)", required = true)
    @field:NotEmpty

```

Reuse `BookInSeriesDto` from `SeriesCreationDto.kt` (same shape as when creating a series).

### 7.5 Controller Endpoint

```kotlin
@Operation(summary = "Register new books into an existing series")
@PostMapping("v1/series/{seriesId}/books")
@PreAuthorize("hasRole('ADMIN')")
fun addBooksToSeries(
    @PathVariable seriesId: String,
    @Valid @RequestBody dto: AddBooksToSeriesDto,
): SeriesDto {
    val series = seriesRepository.findByIdOrNull(seriesId)
        ?: throw ResponseStatusException(HttpStatus.NOT_FOUND, "Series not found")

    val library = libraryRepository.findByIdOrNull(dto.libraryId)
        ?: throw ResponseStatusException(HttpStatus.BAD_REQUEST, "Library not found")

    require(series.libraryId == library.id) {
        "Series does not belong to library"
    }

    val books = dto.books.map { b ->
        Book(
            name = b.name,
            url = URL(b.url),
            fileLastModified = b.fileLastModified.atZone(ZoneId.of("UTC")).toLocalDateTime(),
            fileSize = b.fileSize,
            fileHash = b.fileHash ?: "",
            seriesId = series.id,
            libraryId = library.id,
        )
    }

    seriesLifecycle.addBooks(series, books)

    return seriesDtoRepository.findByIdOrNull(seriesId, null)!!
}
```

**Note:** `tryRestoreBooks` is intentionally skipped — it requires computing
hashes on every new book file (reads entire file), which defeats the speed
advantage of the smart scanner. If restoration is needed, trigger a full
library scan.

### 7.6 Scanner Tool Update

In `applier.py`, replace the `_bld_new_books` library scan fallback with actual per-book API calls:

```python
def _bld_new_books(diff: Diff, library_id: str) -> list[str]:
    if not diff.new_books:
        return []
    lines = []
    # Group new books by their parent series
    # For each book, generate a curl to add it to its existing series
    # Need to know which series each book belongs to
    # Use the diff data — each book URL contains its parent series path
    # Map: series_url → series_id (from _raw_db_series_by_url in diff JSON)
    
    for b in diff.new_books:
        lines.append(f"# Add book to series: {b['name']}")
        # Need series_id — must be resolved from the diff context
        # This requires passing series_id_map to the builder
    return lines
```

To resolve which series each new book belongs to, the `generate_curl_scripts`
function needs access to the series URL → series ID mapping. This data is
available in `_raw_diff` of the diff JSON as `_raw_db_series_by_url`. Pass it
through to the builder.

**Updated `generate_curl_scripts` signature:**
```python
def generate_curl_scripts(
    diff: Diff, library_id: str, categories: list[str],
    analyze: bool, refresh: bool, output_dir: str,
    request_id: str,
    db_series_by_url: dict | None = None,  # NEW

```

The `server.py` gen_curl endpoint reads `_raw_db_series_by_url` from the diff
JSON and passes it to `generate_curl_scripts`.
