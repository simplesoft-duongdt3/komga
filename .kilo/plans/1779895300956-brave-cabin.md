# Rust PDF Hasher — Incremental XXH3_128 Cache

> One-time/incremental Rust CLI that pre-computes XXH3_128 hashes for every
> .pdf in a library, caches results to a JSON file, and on subsequent runs
> only hashes new or modified files. The Python scanner tool reads this cache
> to skip inline hash computation.

---

## 1. Problem

Current Python `_hash()` in `walker.py:23` reads every byte of every PDF via
64KB chunks to compute XXH3_128. This takes **10–35 hours** for 500K files on
Synology HDD. The result is ephemeral — on the next scan, the same files are
hashed again from scratch. No caching.

## 2. Solution

A Rust CLI (`pdf-hasher`) that:

1. Walks the library root, finds all `.pdf` files
2. Loads the existing cache (if any) from `{root}/hashes.json` (or `--cache` path)
3. For each file: if `path + size + mtime` match the cache entry → **skip**
4. For new/changed files → compute XXH3_128 hash in parallel (rayon)
5. Merges old + new entries, **removes stale entries** (deleted files)
6. Atomically writes the merged cache to the cache file

In Docker: cache defaults to `/exports/hashes.json` (writable volume, shared
with smart-scanner). Library volume stays `:ro`.

The Python scanner (`walker.py`) loads `hashes.json` at startup. When
`hash_files=True`, `_hash()` checks the cache first; only misses fall back to
inline Python hashing.

### 2.1 Why Rust

| Factor | Python | Rust |
|---|---|---|
| Hash SIMD | C extension, 1-2 GB/s/thread | Native SIMD, 5-10 GB/s/thread |
| Parallelism | GIL serializes per-byte processing | Rayon — true parallel file hashing |
| Memory-map | `mmap` stdlib, ~30% slower | `memmap2`, zero-copy hash on slice |
| File overhead | CPython `open()` per 64KB chunk | Single `BufReader` per file, 256KB buffer |
| Binary | Not applicable (Python process) | Static 5 MB binary, no runtime deps |

The dominant bottleneck is **I/O** (NAS HDD), not CPU. Rust's advantage is
keeping the I/O pipeline saturated: zero-copy mmap for small files, large
buffers for streaming, and true parallel reads without GIL stalls.

## 3. Cache Format (`hashes.json`)

```json
{
  "type":   "XXH3_128 hash cache",
  "version": 1,
  "generated_at_unix_secs": 1716840000,
  "root":   "/data",
  "elapsed_secs": 1234.5,
  "total_files": 500000,
  "total_bytes":  12500000000000,
  "entries": {
    "file:///data/SeriesA/ch001.pdf": {
      "hash":  "a1b2c3d4e5f6a1b2c3d4e5f6a1b2c3d4",
      "size":  12345678,
      "mtime_secs": 1716839950
    },
    "file:///data/SeriesB/ch042.pdf": {
      "hash":  "f6e5d4c3b2a1f6e5d4c3b2a1f6e5d4c3",
      "size":  87654321,
      "mtime_secs": 1716821000
    }
  }
}
```

- Keys are `file://` URIs (matching Python `Path.as_uri()` output in `walker.py:40`)
- `size` + `mtime_secs` enable **change detection without re-reading** the file
- `root` field records the scan root for debugging
- `total_files` and `total_bytes` provide quick stats without iterating all entries

## 4. Incremental Logic

```
On startup:
  1. Walk ${ROOT} → collect all .pdf files with (path, size, mtime_secs)
  2. Load hashes.json (if exists) → map[path_uri] = {hash, size, mtime_secs}
  3. Classify each file:
     ┌──────────────────────────────────────────────────────────┐
     │  File not in cache                          → HASH       │
     │  File in cache, size == cached.size          → SKIP      │
     │    AND mtime_secs == cached.mtime_secs                   │
     │  File in cache, size or mtime differs        → REHASH    │
     └──────────────────────────────────────────────────────────┘
  4. Hash "HASH" + "REHASH" files in parallel (rayon)
  5. Final cache = cached SKIP entries + freshly hashed entries
     (Files that exist in cache but NOT on disk are dropped)
  6. Atomic write: write to hashes.json.tmp → fsync → rename
```

On first run (no cache exists): all files are "HASH", full population.

#### `main.rs` — key functions

```rust
/// CLI args
struct Args {
    root: PathBuf,           // --root /data
    cache: PathBuf,          // --cache /data/hashes.json (default: {root}/hashes.json)
    threads: usize,          // -j 4 (default: CPU count / 2)
}

/// A single cache entry
struct CacheEntry { hash: String, size: u64, mtime_secs: i64 }

/// Top-level cache (loaded from / written to hashes.json)
struct HashCache { type: String, version: u8, root: String,
    generated_at_unix_secs: u64, elapsed_secs: f64,
    total_files: usize, total_bytes: u64,
    entries: HashMap<String, CacheEntry> }

/// Walk filesystem: collect (path, size, mtime_secs) for all .pdf files
fn collect_files(root: &Path) -> Vec<(PathBuf, u64, i64)>

/// Load existing cache or return empty
fn load_cache(path: &Path) -> HashMap<String, CacheEntry>

/// Hash one file: ≤100MB → memory-map (zero-copy); >100MB → buffered 256KB chunks
fn hash_file(path: &Path) -> io::Result<String>

/// Main flow:
///   1. collect_files(root) → current file list
///   2. load_cache(cache_path) → old entries
///   3. Diff: determine which files need hashing
///   4. rayon::par_iter → hash in parallel (thread pool)
///   5. Merge: skip-valid old entries + new entries (drop stale)
///   6. atomic_write(cache_path, merged)
```

#### CLI usage

```bash
# First run — full population
pdf-hasher --root /data --threads 4

# Subsequent run — incremental (only new/changed files)
pdf-hasher --root /data --threads 4

# Custom cache location
pdf-hasher --root /data --cache /exports/hashes.json -j 8
```

### 5.3 Python Integration

#### `walker.py` — cache-aware `_hash()`

```python
import json
import os

_HASH_CACHE: dict[str, str] | None = None
_HASH_CACHE_PATH: str | None = None

def load_hash_cache(path: str | None = None) -> int:
    """Load the Rust-generated hash cache. Returns number of entries loaded."""
    global _HASH_CACHE, _HASH_CACHE_PATH
    if path is None:
        path = os.environ.get("HASH_CACHE", "/exports/hashes.json")
    if not os.path.isfile(path):
        return 0
    try:
        with open(path) as f:
            data = json.load(f)
        entries = data.get("entries", {})
        # Extract just the hash string for fast lookup
        _HASH_CACHE = {uri: e["hash"] for uri, e in entries.items()}
        _HASH_CACHE_PATH = path
        return len(_HASH_CACHE)
    except Exception as e:
        print(f"[walker] Failed to load hash cache: {e}")
        return 0

def _hash(path: Path) -> str:
    # Check cache first
    if _HASH_CACHE is not None:
        uri = path.as_uri()
        if uri in _HASH_CACHE:
            return _HASH_CACHE[uri]
    # Fallback: compute inline
    ...
```

#### `config.py` — new env var

```python
HASH_CACHE = os.environ.get("HASH_CACHE", "/exports/hashes.json")
```

#### `server.py` — load cache on startup / at scan start

```python

FROM debian:bookworm-slim

```

#### `docker-compose.yml` — add pdf-hasher service + use writable volume

```yaml
  pdf-hasher:
    build:
      context: ./scan-library-tool
      dockerfile: Dockerfile.hasher
    container_name: komga-pdf-hasher
    volumes:
      - /volume1/Shared/my-library:/data:ro        # read-only for PDFs
      - /volume1/docker/komga-tool-scan/outputs:/exports:rw  # cache + exports
    # One-shot: docker compose run --rm pdf-hasher --root /data --cache /exports/hashes.json -j 4
```

Note: The library volume stays `:ro` for both Komga and the hasher. The cache
file lives in `/exports` (the writable shared volume) by default. The `--cache`
flag allows the user to place it elsewhere.

## 7. Workflow

```bash
# 1. Build the hasher
docker compose build pdf-hasher

# 2. First run — full population (run as one-shot)
docker compose run --rm pdf-hasher \
  --root /data --cache /exports/hashes.json -j 4

# 3. Smart-scanner scan (auto-picks up cache via HASH_CACHE env)
#    The scan's Step 2 will use cached hashes, no I/O for hashing.
#    Log shows: "[walker] Loaded hash cache: 500000 entries from /exports/hashes.json"

# 4. After adding/modifying files in the library, update cache:
docker compose run --rm pdf-hasher \
  --root /data --cache /exports/hashes.json -j 4
#    → "Hashed 12 files (cached 499988, stale 0 removed) in 4.2s"

# 5. Re-run scan — instantly uses updated cache
```

## 8. Edge Cases & Decisions

| Edge case | Handling |
|---|---|
| **First run, no cache** | All files hashed; write full cache |
| **File deleted from disk** | Entry removed from cache on next hasher run |
| **File size/mtime unchanged, content changed** | _Not detected_ — requires full re-hash. Assumption: content changes always alter size or mtime (holds 99.9% of the time for Komga's PDF use case). If this is a concern, add `--force` flag for full re-hash. |
| **Concurrent pdf-hasher runs** | Last-write-wins (atomic rename, no file locking). User should serialize manually. |
| **Very large cache (500K entries → ~120MB JSON)** | Load entire cache into HashMap (~150MB RAM). Acceptable: Rust hasher is a one-shot tool, not a long-running service. |
| **Non-UTF-8 paths** | `file://` URIs are percent-encoded by Rust via `urlencoding` of the percent-encoding crate (or manual implementation). |
| **Cache file corrupted** | Fail on load with clear error. User deletes cache file, re-runs. |
| **Python _hash() fallback** | If cache is loaded but a file URL is missing, Python falls back to computing the hash inline. Cache is an optimization, not a requirement. |
